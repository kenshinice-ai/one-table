## 3. 当前已知根因与设计证据

### 3.1 筛选不联动的根因

当前 `src/components/planner-app.tsx` 中：

- `menu` 被保存为独立 state。
- `updateFilters` 和 `updatePreferences` 只更新条件与 revision。
- `composeMenu(...)` 只在点击 `recompose()` 时执行。
- 所以用户选择条件后，右侧继续显示旧菜单，只出现“条件已改变，请重新组合”。

这不是文案问题，而是状态派生关系错误。

### 3.2 筛选文字不可读的根因

线上约 1356px 视口中：

- 筛选面板内容宽度约 446px。
- `.filter-grid` 使用 4 列。
- 每列实际只有约 105px。
- 标签和值同时使用 `nowrap + ellipsis`。

因此大量关键筛选名称和值被截断。

### 3.3 顶部区域过重

线上约 1356px 视口中：

- Hero 主标题约 63.7px。
- Hero 介绍区约 169px 高。
- 菜谱数量在顶部和 Hero 中存在重复视觉表达。

本轮应减少重复、降低尺寸，但保持暖白、陶土橙、鼠尾草绿和编辑感美食产品气质。

## 4. P0：修复筛选与菜单自动联动

### 4.1 目标行为

以下任意条件完成一次选择后，右侧菜单都必须自动更新：

- 菜系与地区。
- 烹饪方式。
- 希望包含食材。
- 不希望出现食材。
- 饮食偏好。
- 排除过敏原。
- 可用设备。
- 单道最长时间。
- 最高辣度。
- 儿童友好。
- 用餐人数。
- 菜品数量。
- 上菜方式。
- 总预算。
- 组合重点。

### 4.2 推荐实现方向

1. 菜单应由 `recipes + filters + preferences + variation` 派生。
2. 如果 `composeMenu` 在 200 条数据下仍能稳定低于 100ms，优先使用 `useMemo`，不要用 `useEffect` 再制造一份同步派生 state。
3. 修改筛选或餐桌条件时，将 `variation` 重置为 `0`，展示当前条件下排名最高的菜单。
4. “重新组合”改为“换一组 / Show another”，只在当前条件下增加 `variation`。
5. Undo 和 Reset 之后也必须自动重新计算。
6. 菜单、价格、时间、热量、蛋白质和状态必须来自同一份条件快照。
7. 删除用户必须手动重新组合才能看到正确结果的门槛。

### 4.3 更新状态

- 同步计算足够快时，直接原子替换结果。
- 如确实需要短暂异步或 debounce，旧菜单可以在极短更新期间保持可见，但必须显示“正在更新菜单…”并设置 `aria-busy`。
- 更新完成显示“已按当前条件更新”。
- 用 `aria-live="polite"` 宣布更新完成、部分结果和空结果。
- 不再把“条件已改变，请重新组合”作为正常操作流程。

### 4.4 空结果与部分结果

- 0 个符合条件：立即移除旧菜单，显示具体冲突原因和可操作的放宽建议。
- 无法满足角色配额：显示缺少哪个菜单角色。
- 必选食材无法覆盖：列出无法覆盖的必选项。
- 只能组成部分菜单：只显示满足全部硬性条件的安全菜品，并明确“只能组成 N/M 道”。
- 绝不能用不符合条件的旧菜或不安全候选补足数量。
- 过敏原的 `contains`、`derived_from`、`may_contain` 和 `unknown` 必须继续全部阻断。

### 4.5 “换一组”要求

- 只在同一条件的有效候选池中轮换。
- 候选池大于 1 时不应连续返回相同组合。
- 候选池只有 1 个时给出明确提示。
- 切换后所有汇总指标同步更新。

## 9. 完成 200 道菜的统一视觉图片

上一批 Luna-Max 生成的图片风格已经获得确认，必须延续该风格，不重新设计视觉方向。

### 9.1 范围

- 首先运行媒体审计，确认当前真实图片数量、缺图数量和元数据状态。
- 保留现有已确认满意的图片，不覆盖、不重新生成。
- 为所有缺图的现有菜谱补图。
- 为所有新增菜谱生成图片。
- 最终必须达到：200 条可用菜谱对应 200 个唯一图片文件和真实媒体元数据。
- 历史基线曾为 31 张已生成、49 张缺图、再新增 120 道；若代码已继续推进，以当前审计为准计算剩余工作。

### 9.2 风格参考流程

1. 从现有图片中选取 3–5 张质量最好的图片作为视觉参考。
2. 使用 ImageGen/imagegen 时把这些参考风格作为系列基准。
3. 不修改已确认参考图。
4. 每张新图读取具体菜谱的标题、canonical ingredients、菜系、做法和角色。
5. 分批生成，每批建议 20–30 张。
6. 每批完成后先视觉审计和媒体审计，再继续下一批。
7. 单张失败只重试该张，不重生成整个批次。

### 9.3 统一视觉风格

- 写实、高质量、现代美食编辑摄影。
- 温暖、自然、清新的聚餐氛围。
- 暖白或浅米色桌面。
- 柔和自然光与轻柔阴影。
- 鼠尾草绿、柔和陶土橙、浅桃色作为少量餐巾或背景点缀。
- 食物为绝对主体，构图干净，留白适度。
- 真实可食用，避免塑料质感和夸张广告感。
- 4:3 横向构图。
- 1600×1200 源尺寸。
- WebP 输出。
- 与右侧菜单卡裁切比例兼容。

### 9.4 菜品真实性

- 图中主要食材必须来自对应菜谱的 canonical ingredients。
- 不得出现未声明的肉类、坚果、乳制品、海鲜、蛋、芝麻或其他重要过敏原。
- 蒸、烤、炒、炖、煮等成品表现必须符合菜谱方法。
- 摆盘可优化，但不能改变菜品身份。
- 地域菜应保留合理特征，不能全部使用同一西式摆盘模板。
- 素食和纯素菜不得出现肉类、动物性酱汁或错误装饰。
- 图片不是安全证明，过敏原仍以结构化数据和包装标签为准。

### 9.5 多样性

- 保持系列一致，但不能让 200 张使用同一构图。
- 合理轮换 45 度视角、轻俯拍和局部近景。
- 盘、碗、托盘和共享餐盘根据菜品角色变化。
- 主菜、配菜、沙拉、汤、主食、前菜、小吃和甜品应有视觉区分。
- 相邻菜单卡避免连续使用高度近似的器皿、背景和角度。
- 不允许通过加入无关食材制造差异。

### 9.6 严格禁止

- 文字、标题、水印、Logo 和品牌包装。
- 人物、手或正在夹取食物的动作。
- 明显 AI 畸变、悬浮食材、重复食材、错误餐具结构。
- 不自然蒸汽、过度油亮、霓虹色或高饱和滤镜。
- 与菜谱不符的装饰和未声明过敏原。
- 同一图片复用到多个 slug。
- 图片不存在时伪造 `generatedAt`。
- 把 AI 图片标记成真实摄影。

### 9.7 文件与元数据

- 运行时图片路径与现有组件保持一致，优先使用 `public/media/{recipe-slug}.webp`。
- slug、文件名和 RecipeImport 记录一一对应。
- `mediaType` 使用 `ai_illustration`。
- `altZh` 和 `altEn` 准确描述具体菜名，并明确其为示意图/illustration。
- `aiPrompt` 保存实际使用的菜谱专属提示词。
- `aiModel` 保存实际模型标识。
- `generatedAt` 只在文件生成成功、写入正确路径并通过基本检查后设置。
- `width=1600`、`height=1200`、`mimeType=image/webp`。
- 不篡改审核字段来掩盖缺图。

### 9.8 图片质量检查

- 每批打开并视觉检查，不只检查文件存在。
- 检查菜品身份、食材、方法、地域特征、构图、色彩和 AI 瑕疵。
- 检查小尺寸卡片裁切后主体清楚。
- 检查图片 width/height 或 aspect-ratio 已保留，避免 CLS。
- 非首屏图片使用 lazy loading。
- 最终 media audit：200 条媒体记录、200 个图片文件、0 缺失、0 重复 slug。
- 随机人工抽检至少 40 张，并覆盖全部菜系组和菜品角色。
