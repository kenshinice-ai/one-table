## 一、图片：不等全量，立即滚动采用（结论）

**现状核查**：E/F 200 道中 **73 张主图已落盘**（前菜 30 / 汤 25 / 沙拉 12 / 其他 6），抽检风格与第一批一致、无未声明食材；但三档尺寸 0 张、`generatedMedia` 写回 0 条——**线上一张都没生效**，全部还在走占位图。

**决策：滚动采用，每批到货每批上线。** 理由：

1. 占位图机制天生支持部分采用——有图走图、无图走占位，不存在「半成品状态」。73 张里前菜/汤/沙拉恰是课程结构上线后最缺图的三类，先上它们对体验提升最大。
2. 越早上线越早暴露风格漂移——60 张时纠偏比 200 张时便宜三倍。
3. 商务在跑：demo 拜访时详情页多一张真图就多一分说服力，没理由压着 73 张不用。

**分工修订（重要）**：原 prompt 让 Luna-max 自己跑 `media:sizes` 并写回 `generatedMedia`——实际执行显示它顾不上，且我们双方在同一仓库已多次撞 git 锁。**改为 Luna-max 只产图、只提交图片文件；尺寸生成、写回、校验、部署全部由我方接管**（采用管线见 C0，每批 15 分钟）。V3 prompt 已按此收窄。

**质检门（每批过一遍再上线）**：抽 20% 对照食材表查未声明食材（过敏原红线）→ 与旧图并排查批次感 → 尺寸 4:3/1600×1200 → 超 300KB 的主图重编码（本批最大 337KB，轻微超标，重编码即可）。

## 二、产品改良建议（按优先级）

**P0 · 商用试点的硬前置**（拜访/签约前必须有）

1. **匿名埋点计数**：scan / compose / list-export / route-save 四个计数器（Workers Analytics Engine，无 cookie 无个人数据）——campaign 结案报告的数据源。现在一个数都拿不出来，这是商务链路上唯一的硬缺口。
2. **Kiosk 模式（白标清单 W3 遗留）**：吸引屏轮播、大触控、闲置 90s 复位、屏幕二维码把配好的一桌交接到手机。商场拜访的现场演示形态。
3. **Sample Grocer 租户**：单层「通道模式」（zone=通道号、无楼层图，路线卡变通道顺序清单）——亚超扫街的 demo，机制已就位，只差示例数据与一个单层版路线视图微调。

**P1 · 产品增长** 4. **菜谱独立页 `/recipe/[slug]`**：600 张静态页构建期预渲染——SEO 长尾入口（现在整站只有一个 URL，搜索引擎抓不到任何菜）、单菜分享的落点、每菜独立 OG 图。与「保存食谱卡」互补：卡片进群，链接进搜索。5. **场合（occasions）维度**：见第三节 schema——筛选面板加「场合」下拉，首页加专题入口（年夜饭/中秋/快手周中）。这是把 wave-3 内容红利变成界面能力的一步，也是白标租户「节庆版」的数据基础。6. **浏览视图 + 本地收藏**：「N 道菜符合条件」点开按课程分组浏览（V2 计划 4.2 的遗留）；收藏与最近菜单存 localStorage——无账号红线不破，PWA 用户价值明显。

**P2 · 偿还与延展** 7. **A–D 老 200 道结构化步骤回填**：老菜谱步骤仍是四段模板文，详情页时间轴对它们无用武之地。随 wave-3 生成器升级一并重排（成本已摊薄）。8. 拼音首字母搜索；iOS 壳（B2C 推广时再启动）。

## 三、下一个 200 道（Batch G/H → 总量 600）：按「场合」选，不再按课程补

前两波把课程和菜系的坑填平了（前菜 42/汤 37/沙拉 47），**第三波的选法换轴：跟着商业日历走**。商场买的是节庆 campaign，亚超要的是节庆专题——内容直接为它们备货。

**Schema 新增**（向后兼容，老数据不动）：

```
occasions?: Array<'cny' | 'mid_autumn' | 'christmas' | 'easter' |
                  'brunch' | 'afternoon_tea' | 'bbq' | 'weeknight' | 'party'>
```
